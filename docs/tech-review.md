## 0. 전체 구조

**선택 이유**
- **람다 아키텍처:** 배치(Spark)와 실시간(Flink)을 나누고 서빙 DB(PostgreSQL)에서 합친다. 경기 기록은 하루 단위 확정 처리로 충분하지만, 진행 중 경기는 초 단위 반영이 필요해 두 경로가 따로 필요했다.
- **ELT(원천 먼저 저장):** 가공 전 원본을 HDFS에 그대로 남겨, 가공 규칙이 바뀌어도 원천부터 다시 처리할 수 있게 했다.
- **Docker Compose 한 번으로 전체 실행:** 서비스 21개를 프로필(app, batch, stream, search)로 묶었다.

**구현**
- 배치: `KOVO API → 수집기 → Kafka → Flink(원천 보관) → HDFS → Spark(정제·분석) → PostgreSQL → Django API → Vue`
- 실시간: `수집기 → Kafka → Flink → Kafka → SSE 게이트웨이 → 브라우저`

**CS 지식**
- 관심사 분리: 수집기는 Kafka에 보내기만 하므로 처리 쪽이 죽어도 수집은 멈추지 않는다.
- 서빙 계층은 조회만 하고, 무거운 계산은 파이프라인에서 미리 끝낸다.

**배운 점**
원천 보관 덕분에 포지션 코드 오류, 수상 문장 파싱 같은 규칙을 몇 번이고 고쳐 다시 돌릴 수 있었다. ELT의 가치는 "다시 할 수 있다"에 있다.

## 1. 데이터 수집 (KOVO)

**선택 이유**
KOVO 웹사이트가 내부적으로 JSON API(`user-api.kovo.co.kr`)를 쓰는 것을 사이트 코드에서 확인했다. Selenium이나 HTML 파싱 없이 `requests`로 충분했다.

**구현**
- 수집기 4종(시즌·일정·경기 상세·문자중계)이 공통 뼈대(`BaseCollector`)를 공유한다. 실행 ID 발급, 수집 기록, Kafka 발행, 실패 보고를 한 곳에서 처리한다.
- 1초 1회 요청 제한. Airflow 작업 여러 개가 동시에 돌아도 지켜지도록 파일 잠금으로 공유한다.
- 429·5xx는 2·4·8초 간격으로 재시도(지수 백오프), 4xx는 재시도하지 않는다.
- User-Agent에 프로젝트를 밝히고, 브라우저인 척하는 헤더는 보내지 않는다.

**CS 지식**
- 지수 백오프로 서버 부담을 줄이는 재시도
- 프로세스 간 상호 배제를 위한 파일 잠금(`fcntl`)
- 페이지네이션 종료 조건: 꽉 차지 않은 페이지면 끝. 정확히 배수면 빈 페이지를 하나 더 받아야 끝을 안다.

**배운 점**
- 문자중계는 2023-24 시즌부터만 있다는 사실을 직접 조회해 알았다. 데이터 범위는 문서가 아니라 실제 응답으로 확인해야 한다.
- Git Bash가 `/stat/...` 경로를 Windows 경로로 바꾸는 문제를 겪고, 클라이언트가 그런 경로를 거부하게 했다.

## 2. Kafka

**선택 이유**
수집과 처리를 분리하고, 같은 데이터를 여러 소비자(HDFS 보관, 실시간 계산, 기사 처리)가 따로 읽게 하려고 썼다.

**구현**
- 토픽 8개. 키는 "시즌-경기번호" — 같은 경기의 이벤트가 같은 파티션에 들어가 순서가 보장된다.
- 프로듀서 `acks=all`, 멱등성(idempotence), lz4 압축
- 브로커 하나, KRaft 모드(ZooKeeper 없이)

**CS 지식**
- 파티션 키와 순서 보장(순서는 파티션 안에서만 보장된다)
- 멱등 프로듀서: 재전송해도 중복 저장되지 않는다.
- 컨슈머 지연(lag)

**배운 점**
Metricbeat의 Kafka 모듈은 활성 멤버가 없는 컨슈머 그룹(Flink)을 건너뛴다. 그래서 지연을 재는 서비스(`kafka-lag`)를 직접 만들었다.

## 3. 원천 보관: Flink raw-archiver + HDFS

**선택 이유**
Kafka는 7일만 보관하므로 장기 보관은 HDFS가 맡는다. Flink가 모든 토픽을 패턴 하나로 구독해 날짜별 폴더로 쓴다.

**구현**
- `/raw/topic=…/dt=YYYY-MM-DD/`에 JSON 줄 단위로 쓴다.
- Airflow 센서는 WebHDFS로 "이번 실행의 메시지가 마감된 파일에 다 들어갔는지"를 센다.

**CS 지식**
- 체크포인트와 파일 싱크의 2단계 커밋: 체크포인트가 완료돼야 파일이 마감(`.inprogress` → 정식 파일)되고 오프셋이 커밋된다.
- 세이브포인트로 상태를 보존한 재시작

**배운 점 (실제 사고 세 건)**
1. 작업을 두 번 제출해 모든 메시지가 두 번 저장됐다 → 제출 스크립트가 중복 제출을 막게 했다.
2. 체크포인트 간격이 꺼진 채 돌아 파일이 하나도 마감되지 않았다 → "RUNNING"만 보고 믿으면 안 된다.
3. 커밋된 오프셋에서 재시작했다가 2개 시즌 데이터의 절반을 잃었다 → 항상 최신 체크포인트에서 재시작한다.

## 4. 배치 정제: Spark on YARN

**선택 이유**
21시즌 4,755경기와 랠리 이벤트 수십만 건을 원천 JSON에서 표로 만드는 일이라 분산 처리 엔진을 썼고, 자원 관리는 YARN이 맡는다.

**구현**
- `curate_kovo.py`: 원본 → 항목마다 가장 최근 사본만(중복 제거) → 관리자 보정 → 품질 검사 12규칙 → Parquet + PostgreSQL
- PostgreSQL 적재는 실행마다 전용 staging 스키마에 넣고, 잠금을 건 한 트랜잭션에서 병합한다(`pg_merge.py`).
- "랠리 하나에는 득점(+1)과 실점(-1) 이벤트가 정확히 하나씩 있다"는 규칙을 찾아, 2025-26 시즌 1,042개 세트의 공식 점수를 그대로 재현했다.

**CS 지식**
- 윈도 함수(`row_number`)로 중복 제거
- upsert(있으면 갱신, 없으면 추가)
- advisory lock(애플리케이션이 정하는 이름의 잠금)
- 트랜잭션 원자성: 사이트는 반쯤 병합된 시즌을 보지 않는다.
- 동적 파티션 덮어쓰기

**배운 점**
- 옛 시즌 포지션 코드(L 레프트, Li 리베로)를 두 번 변환하는 버그로 2005~2019 리베로가 아웃사이드 히터로 묶였다. 변환은 한 곳에서 한 번만 해야 한다.
- Django CASCADE는 DB 규칙이 아니라서, SQL로 지울 때는 자식 행을 먼저 지워야 한다.

## 5. 워크플로: Airflow

**선택 이유**
수집 → 보관 확인 → 정제 → 분석 → 예측의 순서와 재시도·실패 알림을 코드(DAG)로 관리한다. 자원을 아끼려고 LocalExecutor를 쓴다.

**구현**
- DAG 10개: 매일 정제(`kovo_daily`), 경기 후 20분마다(`kovo_postgame`), 과거 시즌 백필, 재처리, 기사 수집, 경기 재생, 주간 재학습, 매일 예측, 주간 수상 기록(`kovo_honors`) 등
- 모든 작업은 3번 재시도하고, 실패하면 DB와 메신저 웹훅으로 알린다. 같은 작업이 계속 실패하면 6시간 동안은 다시 보내지 않는다.

**CS 지식**
- reschedule 모드 센서: 기다리는 동안 작업자 슬롯을 비워 준다.
- 동적 작업 매핑(시즌 수만큼 작업 생성)
- 멱등한 작업 설계: 다시 돌려도 결과가 같다.

**배운 점**
놀고 있는 LocalExecutor 작업자 32개가 메모리를 차지해 Spark 드라이버가 메모리 부족으로 죽었다(exit 137). 동시 실행 수를 6으로 제한해 해결했다. 숫자 하나가 장애를 만든다.

## 6. 실시간 경기

**선택 이유**
- 문자중계를 15초마다 조회하는 폴링(KOVO 화면도 5초 폴링)
- 브라우저 전달은 WebSocket 대신 **SSE**: 서버 → 브라우저 한 방향이면 충분하고 일반 HTTP라 단순하다.

**구현**
- 실시간 수집기: 새 이벤트만 보내고, 위치를 DB에 저장해 재시작해도 이어서 보낸다.
- Flink `live-metrics`: 점수, 서브권, 연속 득점, 세트별 지표, 승리 확률
- Django ASGI 게이트웨이가 Kafka를 구독해 브라우저로 밀어 준다.
- 경기가 없을 때는 끝난 경기를 원래 속도(또는 배속)로 다시 보내는 재생기로 같은 경로를 시연한다.

**CS 지식**
- 동적 계획법(DP) 승리 확률: 상태(세트 스코어, 점수, 서브권)마다 "서브권별 득점 확률"로 이길 확률을 메모이제이션한다. 배구는 서브하는 쪽이 불리해서(리시브 쪽 득점 약 70%) 듀스에서는 서브를 받는 쪽이 유리하게 나온다.
- 같은 이벤트를 다시 받아도 결과가 같은 처리(중복 제거)
- SSE 재연결(`retry:`)

**배운 점**
재생 결과는 공식 박스스코어와 정확히 일치했지만, 실제 생중계는 PC가 꺼져 있어 아직 따라가 보지 못했다. 운영 검증은 일정과 환경이 맞아야 가능하다.

## 7. 기사와 검색

**선택 이유**
본문은 저작권 때문에 저장하지 않고 제목·요약·링크만 쓰므로 RSS와 네이버 검색 API면 충분하다. 한글 검색은 Elasticsearch의 nori 형태소 분석기를 쓴다.

**구현**
- 수집기는 배구 기사만 거르고, 추적 파라미터를 지운 정규 URL을 키로 쓴다.
- Flink `article-enricher`: 제목 기반 중복 제거(말머리·"(종합)" 제거)와 팀·선수 태깅. 두 글자 이름은 같은 팀이 함께 나올 때만, 동명이인은 팀으로 구분될 때만 태그한다.
- 통합 검색과 자동완성

**CS 지식**
- 역색인(inverted index), 형태소 분석
- 정규화 키로 하는 중복 판정
- 정밀도 대 재현율(두 글자 이름 규칙)

**배운 점**
Django가 Elasticsearch보다 먼저 켜지면 캐시된 연결이 고장 난 채 남아 모든 검색이 503이 됐다. 연결 오류가 나면 클라이언트를 버리고 다시 만들게 했다.

## 8. 전력 분석

**구현과 선택 이유**
- **팀 Elo:** 경기 결과로 갱신. 세트 차가 클수록 크게 움직이고 새 시즌에는 평균 쪽으로 되돌린다. 2026-11-12에 K 24 → 28, 새 시즌 유지 비율 2/3 → 1/2로 재조정(7시즌 시험 log loss 0.6414 → 0.6387).
- **팀 강약점:** 8개 지표를 리그 내 순위 점수(0~100)로 바꿔 레이더 차트로 그린다.
- **사이드아웃·브레이크:** 서브권별 득점률, 리시브 질에 따른 공격 성공률(문자중계)
- **선수 유형:** Spark MLlib K-means, k는 실루엣 점수로 고르고 유사 선수를 추천한다.
- **선수 폼:** 최근 5경기와 그 전 경기를 비교해, 통계적으로 분명하고 실제로도 큰 변화만 "상승/하락"이라 부른다.

**CS 지식**
- Elo = 온라인 로지스틱 회귀(결과가 들어올 때마다 경사 하강 한 걸음)
- K-means와 실루엣 계수
- 표준오차를 이용한 유의성 판단(z 1.64)
- 효과 크기: 통계적으로 유의해도 작은 변화는 추세가 아니다.

**배운 점**
기준선(팀 Elo)도 같은 노력으로 다시 조정해 보니 좋아졌다. 새 방법과 비교할 때는 기준선도 공정하게 다듬어야 한다.

## 9. 선수 능력치 카드

**선택 이유**
포지션별 능력치를 1~99점으로 보여 주는 카드. 숫자 하나하나에 근거가 있어야 해서 통계로 설계했다.

**구현**
- 점수 = 60 + 12 × z (같은 성별·포지션, 그 시즌과 앞 두 시즌의 자격 선수 기준)
- **축소 추정:** 시도가 적으면 평균 쪽으로 당긴다(3/3 성공을 100%로 보지 않는다).
- **능력치 선별 기준 — 이적 검증:** 팀을 옮긴 선수의 다음 시즌 상관. 그 수치가 팀이 아니라 선수를 따라다니는지 가장 엄격하게 본다.
- **세터 토스:** "같은 공격수가 다른 세터의 공을 받았을 때 대비 득점률"로 공격수 효과를 뺐다.
- **가중치:** 팀 선수들의 종합 점수와 팀 승률의 상관(234 팀-시즌)이 0.713 → 0.738이 되게 조정
- **통산 카드:** 시즌 점수를 출전 세트로 가중 평균, 역대 순위
- **팀 동료 보정(OH 득점력·리시브):** 이적 선수 상관 0.52 → 0.60, 0.44 → 0.51

**CS 지식**
- z 점수, 경험적 베이즈 축소
- 신뢰도(같은 선수의 시즌 간 상관)
- 교란 변수(팀 맥락)
- 과적합: 이적 선수 81명에 λ를 맞추지 않고 뜻이 분명한 값을 골랐다.

**배운 점**
추천했던 개선안 두 개(득점력 정의 변경, 기준 집단 축소)는 실제로 재 보니 효과가 없어 버렸다. 가설은 데이터로 확인하기 전까지 가설일 뿐이다.

## 10. 경기 예측 모델

**선택 이유**
요구사항대로 Spark MLlib로 만들고, 실험 기록과 모델 관리는 MLflow로 한다. 데이터가 약 4,700경기라 단순한 로지스틱 회귀가 랜덤 포레스트보다 잘 일반화돼 계속 이겼다.

**구현**
- **정답:** 세트 스코어 6가지(다중 분류). 홈 승률 = P(3:0) + P(3:1) + P(3:2)
- **특징 18개:** 선수 Elo, 최근 폼, 시즌 누적 지표, 선수단 수준(squad), 상대 전적 등
- **시점 규칙:** 모든 특징은 경기 시작 전에 알 수 있던 값만(as-of 조인). 이번 시즌 능력치 카드는 쓰지 않는다.
- **시간순 분할:** 학습 / 검증 2시즌 / 시험 1시즌. 설정은 Hyperopt 24회 탐색
- **챔피언 규칙:** 지금 챔피언 설정과 새 설정을 같은 데이터로 다시 학습해 겨루고, 이긴 쪽을 전체 데이터로 학습해 등록
- **워크포워드 백테스트:** 각 시즌을 그 이전 시즌으로만 학습해 예측 → 사이트 "예측 검증" 화면
- **선수 Elo(2026-11-12):** 선수마다 점수, 팀 전력 = 예상 출전 명단 점수의 평균, 새 시즌에는 능력치 카드 쪽으로 되돌림. 단독으로 팀 Elo보다 7시즌 모두 좋았고(z 4.0), 모델에 넣어 v8 → v11(log loss 0.6459 → 0.6422)

**CS 지식**
- 데이터 누출(leakage)
- log loss, Brier 점수, 보정(calibration)
- 대응 표본 검정(경기별 차이의 평균과 표준오차)
- 하이퍼파라미터 탐색(TPE)
- 모델 레지스트리와 별칭(alias)

**배운 점**
- 무작위 분할은 미래로 과거를 배우게 해서 성적을 부풀린다. 시간순 분할이 기본이다.
- 새 특징은 단독 성능이 좋아도 기존 모델 안에서는 효과가 줄어든다(선수 Elo: 단독 −0.009 → 모델 안에서 −0.0026). 반드시 실제 모델 안에서 다시 잰다.

## 11. 백엔드: Django + DRF

**구현**
- 조회 전용 REST API 30여 개. 경기 주소는 내부 id가 아니라 "시즌-경기번호"라서 DB를 다시 만들어도 주소가 바뀌지 않는다.
- 회원: 토큰 인증, 로그인 시도 제한(분당 10회), 관심 팀·선수
- 응답 시간 측정(`scripts/measure_latency.py`): 일반 API p95 121ms, 검색 p95 32ms

**CS 지식**
- 백분위수(p95)
- JOIN 팬아웃: 팀 목록 API가 홈 경기와 원정 경기에 동시에 JOIN해 행이 곱으로 불어났다 → 하위 쿼리로 바꿔 381ms → 25ms
- 토큰 인증, rate limiting
- Windows에서 `localhost`가 IPv6를 먼저 시도해 요청마다 약 2초가 더해지는 문제

**배운 점**
측정 도구 자체가 틀릴 수 있다. 처음 측정이 10분 넘게 걸린 원인은 서버가 아니라 `localhost` 해석이었다.

## 12. 프론트엔드: Vue 3

**선택 이유**
UI 라이브러리 없이 직접 구현(라이선스 걱정 없이, 배우기 위해).

**구현**

- 접근성: 포커스 표시, `aria-pressed`, 차트 요약 문장, 움직임 줄이기 설정 존중
- Hallmark "Sport" 테마(경기 기록지 느낌). 색과 글꼴은 토큰 파일(`tokens.css`) 하나에 모았다.
- 글꼴 4종 모두 OFL 라이선스로 확인(`frontend/FONT_LICENSES.md`)
- 팀 컬러: 엠블럼 색을 읽어 대비 4.5:1까지 어둡게
- 반응형: 900px 이하 머리글 두 줄, 카드 격자 1~3열

**CS 지식**
- CSS 우선순위(specificity)
- WCAG 대비 계산(상대 휘도)
- OKLCH 색 공간: 색상은 유지하고 밝기만 조정
- 리플로를 피하는 `transform`·`opacity` 애니메이션

**배운 점**
헤드리스 브라우저 캡처가 페이지 전환 도중을 찍어 "버그"처럼 보였다. 개발자 도구 프로토콜로 실제 상태를 확인하니 정상이었다. 증거는 한 번 더 확인해야 한다.

## 14. 법과 윤리

**결정**
- 1초 1회 요청, 사실 데이터만, 기사는 제목·링크만, 개인정보 수집 안 함, 비영리
- 감독 정보는 구단 사이트 식별 헤더가 필요해 수집하지 않았다.
- 구단 로고·선수 사진은 KOVO가 바닥글에서 "무단 사용 금지"를 고지하고 있어 쓰지 않았다(NFR-02).

**CS·법 지식**
- robots.txt의 의미와 한계(크롤링 허용 ≠ 이용 허락)
- 인라인 링크 판례(직접 침해 아님)
- 저작권법 제30조(사적 이용)·제35조의5(공정 이용)
- 초상권·퍼블리시티권
- OFL 글꼴 라이선스

**배운 점**
"기술적으로 가능한가"와 "써도 되는가"는 다른 질문이다. 첫날 크롤링 적법성부터 검토해 둔 것이 이후 결정의 기준이 됐다.
